# Update Process

Clint's updater keeps a project's frontend synchronized with the latest components, utilities, and fixes from the base repository (`statikbe/craft`). Because we ship frontend fixes continuously through pull requests — not as a single linear version — updates are tracked with a **manifest** plus a per-project **applied log**, instead of a semver number.

This page explains how the system works, how to apply updates to a project, and — most importantly — **how to author an update when you change something in the frontend** so that every existing project receives it.

## How updates work

### Two sources of truth

| File | Lives in | Role |
| --- | --- | --- |
| `clint/updates/index.json` | the `clint-updates` channel branch | The **manifest**: the canonical list of which updates exist and the order to apply them (`seq`). Generated by CI — never hand-edited. |
| `frontend/.clint-applied` | each project (committed) | The **applied log**: a sorted, newline-delimited list of update ids this project has already applied. |

An update is "pending" for a project when its id is in the manifest but **not** in that project's applied log. There is no version comparison anymore — it is a simple set difference.

::: tip Why a line list (and not JSON)?
`frontend/.clint-applied` is committed and configured with `merge=union` in `.gitattributes`, so two developers appending different ids on different branches merge automatically without conflicts.
:::

A gitignored sidecar, `frontend/.clint-applied.meta.json`, stores per-checkout audit data (when each id was applied, by which CLI version, and the migration marker). It is never used for correctness and never merged.

### Update detection

When you run `yarn start`, Clint fetches the manifest and reports how many updates are pending:

```
---------------------------------------------------------------------------
| 🐦‍🔥 There is an update available for the CLI: 0.0.1 -> 0.0.2
| 🎨 2 frontend updates available: Fix card spacing, Rename datalayer events
---------------------------------------------------------------------------
```

The CLI itself still updates by semver (it is a separate concern). The frontend line lists the **titles** of the pending updates.

## Applying updates to a project

Select **Update** from the main menu.

### Safety checks

::: danger Critical: commit your changes
Clint refuses to run if your git working tree is dirty. Commit or stash first — this protects you from losing work and makes the automatic restore-on-failure safe.
:::

A lock file (`frontend/.clint.lock`) prevents two Clint runs from updating the same checkout at once. It is removed automatically when the run finishes.

### Pre- and post-update screenshots

Before applying updates, take "before" screenshots; after, take "after" screenshots and compare them to catch visual regressions.

- **Pre-update check** — screenshots before updating
- **Post-update check** — screenshots after updating

You can screenshot a full sitemap or a single URL, for a local DDEV project or an external URL. See [Tests](/frontend/clint/tests) for the comparison view.

### Selecting what to apply

Pending updates are always applied as a **no-gap prefix** in manifest order — you cannot skip an earlier update and apply a later one:

```
Which updates do you want to apply? (always a no-gap prefix, in apply order)
> Apply all 2 pending updates
  Apply up to: Fix card spacing (20260612-fix-card-spacing)
```

Each update is applied as its own transaction and **recorded the instant it succeeds**. If one fails, Clint stops, restores that update's files, and leaves everything already applied recorded — so re-running resumes from the one that failed.

### First run / migration

A project that predates this system has no `frontend/.clint-applied`. On the first update Clint runs a one-time **migration**: it reads the legacy `version` from `frontend/package.json`, marks every manifest entry up to that version as already applied (after a dry-run preview and confirmation), and writes the applied log.

::: warning Commit the applied log
After migration, commit `frontend/.clint-applied` before continuing — in a shared project the next run's clean-tree check depends on it.
:::

### CLI updates

When Clint itself needs updating, it downloads the latest CLI code, runs `yarn install` and `yarn build`, and then exits. **Restart Clint** to continue with frontend updates.

## Anatomy of an update

Updates live in `clint/updates/`, one folder per update. New updates are named with a **date-slug** (`<YYYYMMDD>-<kebab-title>`); the legacy `1.0.x` folders keep their names.

```
clint/updates/
├── index.json                       ← the manifest (CI-generated)
├── 1.0.9/                           ← legacy update (kept as-is)
│   ├── update.json
│   └── CHANGELOG.md
└── 20260612-fix-card-spacing/       ← a new update
    ├── update.json
    └── CHANGELOG.md
```

### `update.json`

Metadata plus the (optional) file operations. An update with **no** `frontend`/`root` block is a valid "record-only" update — common when the change is documentation or when the file sync is fully covered by normal syncing.

```json
{
  "id": "20260612-fix-card-spacing",
  "title": "Fix card spacing",
  "description": "Corrects the gap between cards in the grid component.",
  "date": "2026-06-12",
  "issues": [612],
  "pr": 640,
  "requires": [],
  "frontend": {
    "modify": ["js/components-site/card.component.ts"],
    "findAndReplace": [
      {
        "files": ["../templates/**/*.twig"],
        "from": "/gap-3/g",
        "to": "gap-4"
      }
    ]
  },
  "root": {
    "modify": ["vite.config.js"]
  }
}
```

**Metadata fields**

- `id` — must equal the folder name (CI enforces this).
- `title` — shown in the menu and changelog.
- `description` — printed while applying.
- `date` — `YYYY-MM-DD`; with `id`, determines apply order.
- `issues` / `pr` — for linking only; **never** used for ordering.
- `requires` — ids of updates that must be applied first. Validated as a hard gate.

**`frontend` section**

- `modify` — files to **force-sync** from the base repo even if they are in `frontendExcludeFromSync` (e.g. `js/components-site/*`). Files not in the exclusion list sync automatically and don't need listing.
- `findAndReplace` — automated code transformations (see below).

**`root` section**

- `modify` — root-level files (outside `frontend/`) to sync.
- `findAndReplace` — transformations for root-level files.

#### Find & replace

Clint uses [replace-in-file](https://www.npmjs.com/package/replace-in-file). Each rule has:

- `files` — glob of files to search (e.g. `"../templates/**/*.twig"`).
- `from` — the pattern. `"/pattern/g"` becomes a **global regex**; anything else is a **literal string**.
- `to` — the replacement.

::: warning Write idempotent rules
Updates may be re-attempted after a failure, so a rule's `from` must match **only the pre-change state**, so re-running is a no-op. Prefer renaming (`gap-3` → `gap-4`) over appending. Note: a **plain-string** `from` replaces only the **first** occurrence — use the `/.../g` regex form for all occurrences. A rule whose target files don't exist now **fails loudly** rather than silently passing.
:::

### `CHANGELOG.md`

Markdown, opened in Chrome after the update applies. (Note the upper-case filename.)

```markdown
# Fix card spacing

**Release date:** 2026-06-12

## Summary

Corrects the gap between cards in the grid component.

## Changed

- `gap-3` → `gap-4` on the card grid (automated)

# Manual intervention

> ⚠️ **ATTENTION**:
> Re-check any custom card layouts that override the grid gap.
```

### The manifest (`index.json`)

The published list of updates. Each entry is generated from the folders:

```json
{
  "schema": 1,
  "generatedAt": "2026-06-12T09:00:00Z",
  "updates": [
    {
      "id": "20260612-fix-card-spacing",
      "seq": 9,
      "title": "Fix card spacing",
      "date": "2026-06-12",
      "issues": [612],
      "pr": 640,
      "requires": [],
      "legacyVersion": null,
      "hasOps": true
    }
  ]
}
```

- `seq` — the authoritative apply order, assigned by CI over a `(date, id)` sort. It is never derived from the folder name and never stored in a project.
- `legacyVersion` — set only on migrated `1.0.x` entries; powers migration.
- `hasOps` — whether the update has any file operations.

::: danger Never hand-edit `index.json`
It is regenerated by `clint update:index` and validated/published by CI. Editing it by hand will be overwritten and will fail validation.
:::

## Authoring a frontend change

This is the key workflow. **Editing files under `frontend/` updates the template for new project clones only.** Existing projects receive your change *only* when you also ship an **update folder** that the manifest lists — that is what their Clint detects and applies.

So whenever you change the frontend in a way other projects should get, do both: make the actual change **and** author an update.

### Step by step

1. **Branch off `develop`** on `statikbe/craft` and make your frontend change (edit the real files under `frontend/`, e.g. `frontend/js/...`, components, etc.).

2. **Scaffold the update folder.** Either pick **Author update → New update** in the `yarn start` menu, or run it directly from `clint/` (build the CLI first if needed with `yarn build-cli`):

   ```bash
   node dist/cli.js update:new "Fix card spacing"
   ```

   This creates `clint/updates/<today>-fix-card-spacing/` with a prefilled `update.json` and a `CHANGELOG.md` template.

3. **Fill in `update.json`.** Add the `description`, the `issues`/`pr` numbers, any `requires`, and — if the change needs them — the `frontend` / `root` operations:
   - List a file in `modify` **only** if it is in `frontendExcludeFromSync` but must still be updated (e.g. a `js/components-site` component). Regular shared files sync automatically.
   - Add `findAndReplace` rules for template/code migrations, keeping them idempotent.
   - Omit both blocks for a record-only update.

4. **Write `CHANGELOG.md`** — summary, what changed, and a **Manual intervention** section for anything that can't be automated.

5. **Regenerate the manifest** — pick **Author update → Regenerate manifest** in the menu, or run:

   ```bash
   node dist/cli.js update:index
   ```

   This walks the folders, assigns `seq`, validates each folder (must have `update.json` + `CHANGELOG.md`, `id` must equal the folder name, JSON must be valid), and writes `clint/updates/index.json`. Commit the regenerated `index.json`.

6. **Open a PR into `develop`.** CI (`clint-update-index`) re-validates the folders and checks that the committed `index.json` is current. If it's stale, run `update:index` again and commit.

7. **Merge.** On merge to `develop`, the `clint-publish-updates` workflow force-updates the **`clint-updates`** channel branch to develop's commit. From that moment, every project's Clint sees your update as pending and can apply it.

### Rules to remember

- **Folder name = `id` = `update.json.id`.** Don't use raw issue numbers as the folder name; put issue/PR numbers in the metadata fields.
- **Never hand-edit `index.json`** — always regenerate with `update:index`.
- **`findAndReplace` must be idempotent** (matches only the pre-change state).
- **Use `requires`** if your update genuinely depends on another landing first.
- The frontend `package.json` `version` field is now **legacy** — it is only read during migration. You do not bump it when authoring updates.

## What happens during an update

1. **Pin a commit.** Clint resolves the `clint-updates` ref to one immutable SHA so the manifest and file content can't drift mid-run.
2. **Fetch the manifest** at that SHA and read the project's applied log.
3. **Compute pending** = manifest ids not in the applied log; order by `seq`.
4. **Validate** `requires` and folder/manifest drift; fetch only the selected update folders into a temp directory (never into your working tree).
5. **Apply each update** in order: sync `modify` files from the pinned content, run `findAndReplace`, then **record the id** in `frontend/.clint-applied` on success.
6. **Show the changelog** for the updates applied this run, in Chrome.

## After updating

::: warning Rebuild required
```bash
yarn build
```
:::

1. **Visual check** — compare pre/post screenshots.
2. **Functional testing** — exercise key flows.
3. **Console** — look for JS errors.
4. **Manual interventions** — follow the changelog's "Manual intervention" section (custom components, custom CSS/JS, project-specific Twig).
5. **Commit** `frontend/.clint-applied` along with the synced changes.

## Best practices

::: tip Ship the update with the change
A frontend fix that isn't accompanied by an update folder won't reach existing projects. Author both in the same PR.
:::

::: tip Take screenshots first
Run a pre-update check before applying. Visual regression testing saves time.
:::

::: tip Update regularly
Small, frequent updates are far easier to apply and review than large batches.
:::

::: tip Test in development first
Never apply updates directly to production. Validate locally or on staging.
:::

::: tip Keep find & replace idempotent
Author `from` patterns that match only the pre-change state, so a re-run after a failure is safe.
:::
