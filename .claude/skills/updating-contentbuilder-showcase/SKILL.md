# Updating the content row showcase

`ddev craft statik/contentbuilder` builds the content row showcase ("gridbuilder"): a page tree under the page with slug
`gridbuilder` (`config/custom.php` → `gridbuilderShowcaseSlug`) that shows every column type of the content row (Trinity) in
every layout, next to every other column type. Each row's variation is described in an HTML comment before its section on the
showcase pages (`isShowcase` in `_contentBuilder.twig`); it is not rendered, so the page looks exactly like real output.

There is no showcase per Content Builder block anymore; only content rows are generated.

**All content comes from one file: `config/contentbuilder-showcase/content.json`.** Your job is almost always to edit that file
and rerun the command — not the PHP.

| Piece | Path |
|---|---|
| Content (edit this) | `config/contentbuilder-showcase/content.json` |
| Local images (optional) | `config/contentbuilder-showcase/images/` |
| Command | `modules/statik/src/console/controllers/ContentbuilderController.php` |
| Which fields vary + labels | `modules/statik/src/helpers/ContentbuilderShowcase.php` |
| Variation comment in the frontend | `templates/_site/_snippet/_content/_contentBuilder.twig` (`isShowcase`) |

## Workflow

1. **Inspect the current pages** — always first, column types change over time:
   ```bash
   ddev craft statik/contentbuilder --dry-run
   ```
   This prints every page with its number of rows and layouts, plus warnings for content that is missing or invalid.
2. **Gather content** — scrape (below) or invent (below).
3. **Edit `content.json`** following the format below. Keep field handles exactly as in the cell entry types.
4. **Validate & generate**:
   ```bash
   ddev craft statik/contentbuilder --dry-run   # no warning lines left that you meant to fix
   ddev craft statik/contentbuilder
   ```
   Fix every `!` warning (unknown image key, missing entry URI, unsupported link type, …) and rerun.
5. **Check the result** in the browser (`https://<project>.local.statik.be/nl/gridbuilder/`) — the parent page links to every
   column type page, which links to its combinations. With Playwright, take a screenshot of one or two pages. Mention the page
   URL to the user.

Changed images? Rerun with `--refresh-images` (files are otherwise reused by filename). New image keys are imported automatically.

## The pages

Built by `planGrid()` in the generator:
- **Level 1 – `gridbuilder`** (title and intro from `gridParent` in content.json): cards to every column type, plus cards to the
  Layouts, 2/3 and 3/4 pages.
- **Level 2 – one page per column type** (`gridbuilder/text`, `gridbuilder/image`, …): cards to the combination of that type
  with every column type, itself included.
- **Level 3 – one page per pair of column types**, under the type that comes first in the `gridCells` field
  (`gridbuilder/text/text-image`); the later type's overview links to that same page (the Image page links to "Text + Image").
  Two different types: every layout they fit in (following `minWidthPerType` / `maxWidthPerType` in `config/trinity.php`; a
  type with a maximum below full gets no row on its own; pairs in `blockedCombinations` or without any row get no page, and a type blocked with
  itself or that only fits full rows (Call to action) shows its variants at full width instead), both ways round, and each one on the right with "Mobile order" 1. The same
  type twice (`text-text`): the type alone (full width), next to itself in every layout it fits in, its own field variants at
  1/2 and a row with the right one on "Mobile order" 1. "Mobile order" is left on "Auto" everywhere else.
- **`gridbuilder/layouts`**: every layout and every vertical alignment, and a thirds row with mobile order 3 – Auto – 1.
- **`gridbuilder/two-thirds-page`** / **`gridbuilder/three-quarters-page`**: the builder rendered at 2/3 or 3/4 of the page
  (like a page with a sidebar); only the layouts and column types allowed there (`ContentbuilderShowcase::GRID_PAGE_WIDTH_SLUGS`).

Backgrounds rotate over the rows. Pages of column types or combinations that no longer exist are removed on every run.

The overview pages (levels 1 and 2) are content rows too: per group one full row with a column whose Entries field takes all the
pages and that may be full width, the **Overview** column ("Overview options" Entries, a grid: cards three per row), with the
group title in its own title and no link. Without such a column the generator falls back to the first column with an Entries
field (e.g. Card), repeated as many per row as its width rules allow, below a full row with the title in a Text column; an
incomplete last row then gets an empty Text column.

## content.json format

```jsonc
{
  "meta":       { "theme": "…", "source": "https://scraped-site.be or null", "language": "nl", "updated": "YYYY-MM-DD" },
  "gridParent": { "title": "Gridbuilder", "intro": "<p>Shown in the header of the overview page</p>" },
  "assets":     { "volume": "publicFiles", "folder": "contentbuilder-showcase" },

  // Image pool, referenced by key from Assets fields
  "images": {
    "hero": { "url": "https://…/photo.jpg", "alt": "…", "caption": "…", "copyright": "…" },
    "team": { "file": "images/team.jpg", "alt": "…", "filename": "team.jpg" }   // file = relative to content.json
  },

  // Samples used to show off CKEditor features (see "Rich text" below); all keys optional
  "richText": {
    "link": "https://www.thekindkids.be",          // href for sample links — always this URL
    "bold": "bold text", "italic": "italic text", "linkText": "a link",   // used only when a text lacks them
    "headings": ["…", "…", "…"],                    // one per allowed heading level, cycled
    "listItems": ["…", "<strong>…</strong> …", "…"], // items for the <ul> and the <ol>
    "paragraph": "<p>…</p>"                         // after headings once the lists are used up
  },

  // Excessively long title for the long-title stress example (see below)
  "longTitle": "An excessively long title … including an unbreakable Supercalifragilistic…word",

  // Shared content per FIELD HANDLE — the fallback for every column type that has that field
  "fields": {
    "blockTitle": "Plain string",
    "text": "<p>HTML for CKEditor fields</p>",
    "image": ["hero"],                       // Assets: list of image keys, or "*" for all images
    "cta": [ { "type": "url", "value": "https://…", "text": "Read more",
               "newWindow": false, "fields": { "ctaFieldLinkLayouts": "btn btn--primary" } } ],
    "video": "https://www.youtube.com/watch?v=…",  // Url fields: a string
    "entries": "@showcase"                   // Entries: "@showcase" (the column type pages) or a list of URIs ["news/my-article"]
  },

  // Per row / CELL TYPE HANDLE (win over "fields")
  "blocks": {
    "gridRow": { "partner": "cellText", "visualPartner": "cellImage" },   // the cells next to others on the Layouts and 2/3 pages
    "cellQuote": {
      "fields": { "text": "…", "writer": "…" },
      "fixed":  { "cta": false }                                          // pin a variant (see below)
    },
    "cellFaq":  { "fields": { "faqBlock": [ { "blockTitle": "Question?", "text": "<p>Answer</p>" } ] } },  // nested Matrix: list of items keyed by field handle, optional "type"
    "cellForm": { "fields": { "form": "contact_NL" } },                   // Formie form handle; null = first form
    "cellCard": { "fields": { "blockTitle": "…", "description": "<p>…</p>" } } // fields of a Content Block (cardInfo) are looked up like the cell's own
  }
}
```

Value rules per field type:
- **CKEditor**: see "Rich text" below. A **list of texts** (`["<p>…</p>", "<p>…</p>"]`) rotates over the filled instances, like
  CTA link sets — e.g. different table layouts in the `table` field.
- **Plain text / Title (Anchor)**: plain string, no HTML.
- **CTA fields (`cta`, `ctas`: Link entries)**: list of links, one Link entry per link (`cta` takes one). `type` = `url` |
  `email` | `entry` (value = entry URI, `__home__` for home) | `asset` (value = image key) | `tel`; optional `newWindow: true`
  and `anchor` (becomes the URL suffix `#anchor`). `fields` = the other fields of the Link entry: `fields.ctaFieldLinkLayouts`
  = a key from `config/config-values-field.php` → `CTA styles` (`btn btn--primary`, `btn btn--secondary btn--ext`,
  `link link--ext`, …). For `ctas`, you can also pass a **list of link sets** (`[[link, link], [link], …]`): the sets rotate
  over the filled instances, so the showcase shows every CTA style.
- **Embed** (plain text): full embed HTML; the template only renders it if it contains `src="https:`.
- **Option fields** (Position, Width, Background Color, lightswitches) are **not** content — they are the variants. Don't put
  them in `fields`; pin them with `fixed` instead.
- `null` means "no content here → fallback". To force a field empty, pin it in `fixed` with `false`.

### Rich text (CKEditor fields)
The command reads each CKEditor field's `toolbar` and `headingLevels` at runtime (`config/project/fields/ckEditor*.yaml`) and
makes sure the showcase exercises them:
- **Every instance** contains **bold**, *italic* and linked text (when the toolbar has them). Write the content.json text that
  way: 1–3 short `<p>` paragraphs where some words are `<strong>`, some `<em>` and some are
  `<a href="https://www.thekindkids.be">…</a>` — **always link to https://www.thekindkids.be**, also when scraping (keep the
  scraped link text, replace the href). If a text lacks one, the command appends a sample sentence and warns.
- **One instance per column type per page** (the first one) additionally gets a heading for every allowed level plus a `<ul>`
  and an `<ol>`, built from `richText`. So **don't put headings or lists in the regular texts** — they would appear everywhere.
- Only use tags the field's editor allows; the command warns about others (`<h3>` in the FAQ answer field "without H3", lists
  in the table field, …). Tables go only in the table field, as `<figure class="table"><table>…</table></figure>`. No inline
  styles or classes; never `<h1>`/`<h2>` (titles render as `<h2>`/`<h3>`).
- Write `richText.headings`, `listItems` and `paragraph` in the showcase language and theme too.

### Long titles
Every title field — Title (Anchor) fields (`blockTitle`, FAQ questions) and plain text fields with "title" in their handle —
gets `longTitle` in **the second instance of a column type on a page**. For nested FAQ items it's the first question of that
instance. Keep `longTitle` over 100 characters (that is what marks it `long`), in the showcase language, and include one very
long word **without hyphens** so overflow on small screens is actually tested.

### Pinning variants (`fixed`)
A column type is shown in its variants: every optional field filled and empty, every option field per option. The lightswitches
and option fields in a Content Block field vary too, as `"<block field>.<field>"` (e.g. `cardInfo.imageIsIcon`); its content
fields are filled whenever the block is. Field conditions on another field's value (e.g. Card's Entry field only for "Card
type" Entry) are followed: hidden fields stay empty, and variants that only differ in hidden fields are shown once. Pin one with
`blocks.<cell type>.fixed`: `{ "videoCaption": true }` (always filled), `false` (always empty) or an option value
(`"cardInfo.imageIsIcon": false` for a Content Block's field). Only do this
when the user asks for fewer variations — by default the showcase shows all of them.

## Scraping content from an existing website

Goal: content that represents the real site (tone, text length, real images), mapped onto the column types.

1. Ask for (or use) the site URL. Fetch the homepage + 3–6 content-rich pages (about, services, an article, FAQ, contact). Use
   `WebFetch` for text; use Playwright (`browser_navigate` + `browser_evaluate`) when content is JS-rendered or to collect image
   URLs (`[...document.images].map(i => ({src: i.currentSrc || i.src, alt: i.alt, w: i.naturalWidth}))`).
2. Map what you find onto the cell types:
   - headings → `blockTitle`; paragraphs/lists → `text` (keep realistic length: 1–3 short paragraphs, sometimes a list);
   - buttons/links → `cta` / `ctas` (real link texts, absolute URLs to the scraped site);
   - testimonials → `cellQuote.text` / `writer`; FAQ sections → `cellFaq.faqBlock`; tables (prices, opening hours) → `cellTable`;
   - YouTube/Vimeo links on the site → `video`; maps/iframes → `cellEmbed`.
3. Images: pick 4–6 large photos (≥1200px wide, landscape; one square portrait for `authorImage`). Prefer downloading them into
   `config/contentbuilder-showcase/images/` (`curl -L -o …`) and referencing them with `"file"` so the showcase keeps working
   when the source site changes; otherwise use `"url"`. Always write a meaningful `alt`. Skip logos, icons and tracking pixels.
4. Set `meta.source`, `meta.language`, `meta.updated`. Content is written to **all sites** (nl/fr/en) identically, so use the
   site's main language unless the user says otherwise.
5. The scraped content is for internal/demo use on the showcase; don't copy personal data (names/photos of private people in
   testimonials) — replace author names with a plausible fictional one if unsure.

## Inventing content for a theme

When there's no site ("make it for a zoo", "fitness brand"):
- Write in the requested language (default: the primary site language, `nl-BE`, unless told otherwise); consistent fictional
  organisation name and tone.
- Vary lengths realistically: short punchy titles (3–7 words), body text 40–120 words, CTA texts 1–3 words.
- Images: use themed stock images with stable URLs (e.g. `https://images.unsplash.com/photo-…?w=2400` from a search you
  actually did, or `https://picsum.photos/id/<id>/2400/1600.jpg`). Never invent URLs you haven't verified — check each with
  `curl -sI` (expect `200` and an `image/*` content type).
- Videos: real YouTube/Vimeo URLs that exist (verify).
- Set `meta.theme`.

## When column types changed (new cell type, new field, removed type)

The command reads the cell types and their fields from Craft at runtime — **no PHP changes are needed** as long as their field
types are known:
- New cell type → it gets a page and combinations automatically; add `blocks.<handle>.fields` for its content.
- Removed cell type → its pages are deleted on the next run.
- New/renamed field handle → add content under the new handle; remove the old key.

Only touch PHP when a field type has no fallback (a `No content for …` warning), or a new kind of variant field should vary:
- New variant field type (e.g. a new select-like plugin field) → `ContentbuilderShowcase::dimensionValues()`.
- New content field type (how a content.json value becomes a field value) → `normalizeContent()` / `fallbackValue()` /
  `emptyValue()` in the controller.
