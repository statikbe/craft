# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`statikbe/craft`: Statik's Craft CMS 5 starter (PHP 8.4, MySQL 8, DDEV, Vite + Tailwind 4 + TypeScript). New projects are created from it with `composer create-project statikbe/craft`, then configured with `ddev craft statik/setup`. Changes here therefore ship to future projects, and frontend changes also reach existing projects through **Clint** updates (see below). Release notes for the current release live in `WHATS-NEW.md`.

Project skills in `.claude/skills/` hold the detailed knowledge; load them instead of re-deriving it:
- `understanding-project-architecture`: module, plugins, multi-site, content builder / content rows (Trinity), page header, calendar, team, partners
- `working-with-ddev`, `working-with-github-cli`, `checking-code-guidelines`, `authoring-clint-updates`, `exporting-figma-theme`, `updating-contentbuilder-showcase`, `removing-contentbuilder-showcase`

## Commands

All PHP / Composer / Craft commands run through DDEV, never on the host:

```bash
ddev craft up                      # migrations + project config apply
ddev composer check-cs             # ECS (modules/ only, Craft 4 ruleset; this is what CI runs)
ddev composer fix-cs
ddev composer phpstan              # level 2, modules/ only
ddev craft statik/contentbuilder   # (re)build the content row showcase pages
ddev craft headings-checker/check  # heading order audit (Headings Checker plugin)
ddev craft link-checker/report     # broken links in the content (Link Checker plugin); link-checker/rebuild reads every page again
ddev craft statik/dummy-content/news [--count=12] [--dry-run]   # dummy news; statik/dummy-content/clean news removes it
```

There is no `package.json` at the root. Frontend commands run from `frontend/` (Yarn 1):

```bash
yarn watch     # Vite dev server with HMR (https://localhost:3000); also checks for Clint updates
yarn prod      # production build to public/frontend/
yarn ckeditor  # separate CKEditor bundle
yarn favicon   # from frontend/img/favicon.svg
```

There is no unit test suite. Site tests (a11y, HTML validation, links, CO2) run through Clint: `cd clint && yarn build && yarn start` (needs `NODE_EXTRA_CA_CERTS` from mkcert, set by the start script). Docs site: `cd docs && yarn docs:dev` (VitePress, `docs/src/`; `docs/` is export-ignored so projects don't get it).

Local site: `https://craft-base-install.local.statik.be`.

## Architecture

- **Config**: `config/general.php`, `db.php` use the legacy multi-environment array syntax (production / staging / dev). `config/project/` is the project config (fields, sections, entry types, Formie forms); change structure through it and apply with `ddev craft up`.
- **Custom module** `modules/statik/src/` (namespace `modules\statik\`, registered in `config/app.php`): language routing via `__language` cookie, Twig extensions (`render_image`, `render_ctas`, `obfuscate_emails`, `tel`, icons, hyphenation, …), console controllers in `console/controllers/`, dashboard widgets, maintenance mode, security headers.
- **Templates**: `templates/_site/` holds all site templates, sorted by role (`GUIDELINES.MD` §5): `layout.twig` (the base), `pages/` (section templates), `contentBuilder/`, `components/` (`frame/`, `pageHeader/`, `cards/`, `partials/`) and `macros/`. The content builder dispatcher `_site/contentBuilder/contentBuilder.twig` includes `blocks/<entryTypeHandle>.twig`, so a block's entry-type handle maps 1:1 to its template. Content rows (`gridRow`, 1–3 columns of `cell*` column types) are rendered from `contentBuilder/gridRow.twig` and `contentBuilder/columns/`; their rules and validation live in the Trinity plugin, configured in `config/trinity.php`.
- **Multi-site**: NL / FR / EN (`nl-BE`, `fr-BE`, `en-BE`), URLs `@baseUrl/{nl,fr,en}`.
- **Frontend**: entry `frontend/js/site.ts` registers components that `ComponentLoader` lazy-loads by CSS selector. Site components go in `frontend/js/components-site/`, shared ones in `components-core/`. Theme tokens in `frontend/css/site/theme.css`. A second site has its own entry/config (`site2.ts`, `vite.config.site2.js`).
- **Clint** (`clint/`): Statik's frontend updater and site tester. Frontend changes that existing projects should receive need an update folder in `clint/updates/<id>/` (`update.json` + `CHANGELOG.md`); use the `authoring-clint-updates` skill. `clint/updates/index.json` is generated by CI on the `clint-updates` branch and must not be committed.

## Conventions

- Follow `GUIDELINES.MD` (naming: content + type, lowerCamelCase handles and templates, sentence case labels, English names with translations). Check with the `checking-code-guidelines` skill.
- Templates inside `_site/` have no `_` prefix and follow the folder structure of `GUIDELINES.MD` §5. Projects started from the base install before the move keep the old `_snippet/` structure, so a Clint update that changes a template must still work with the old path there.
- Translations: `translations/` is gitignored in this repo. The tracked copies are in `setup-translations/<language>/` (copied by `statik/setup`), so write new keys there too. CP translations go in the general language folder (`nl/`, `fr/`), not `nl-BE/`.
- Git: PRs target `develop`; `develop` deploys to staging, `master` to production. CI (`.github/workflows/ci.yml`) runs ECS only.
- `.githooks/` (enabled by `yarn start` in `frontend/`) runs `ddev craft up`, `composer install` and a frontend build after pulls that touch those files.
